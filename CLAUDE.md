## What this project is

Runewright is a decentralized, in-person mobile wizard-dueling game. Players inscribe
spells by designing initial states of a hexagonal cellular automaton (CA), generate a
zero-knowledge proof that the simulation ran correctly, and duel peer-to-peer over local
wireless. No server, no accounts, no central authority.

- **Client:** Flutter / Dart (Android first).
- **ZK:** Noir circuits + Barretenberg (UltraHonk) backend; Poseidon2 in-circuit hashing.
- **Current focus:** the **cryptographic core** only (see Scope). Not the full game.

## Hard invariants — never violate these

These are the load-bearing security and correctness rules. Breaking one is a bug even if
everything compiles and tests pass.

1. **Never reimplement Poseidon2 (or any hash) in Dart.** The client reads `commitment`
   from the prover's public inputs and treats it as **opaque**. The only Poseidon2
   implementation is the one in the Noir stdlib, inside the circuit.
2. **The commitment is grid-only:** `commitment = Poseidon2(packed_grid)`. Never fold
   `T`, a salt, `owner_pubkey`, or `ruleset_version` into it — doing so silently breaks
   counter-charm targeting. Those are all *separate* public inputs.
3. **Every cell is constrained to {0,1}** — all 469 of them, no exceptions. Buffer +
   border cells (index ≥ 217) must be 0 at T=0. Under-constraining cells is the classic
   ZK exploit vector.
4. **Every circuit change must pass the full golden corpus — positive AND negative —
   before it is committed.** A circuit that's faster but accepts a witness it shouldn't
   is worse than no change. The negative vectors are the spell-leak backstop; treat a
   failing negative vector as a release blocker.
5. **All signatures are off-circuit Ed25519.** The circuit never verifies a signature.
   It only *binds* `owner_pubkey = Poseidon2(key halves)` as a public input. Cast-time
   challenges, loans, scrolls, and match records are all Dart-side Ed25519.
6. **Three circuit tiers, `tier_max ∈ {12, 24, 48}`.** Don't hardcode a single T. Arrays
   are `[Field; tier_max]`; the handshake picks the smallest tier covering the declared
   `T`; `1 ≤ T ≤ tier_max`.
7. **Identity is local and self-custodied.** Keypair generated on first launch, stored
   on-device, no server, no account. Losing the key or spellbook is the user's risk
   (the UI must say so) — never add a recovery backdoor or phone-home.

## Toolchain

- **Flutter / Dart** — primary client. Ubuntu Linux + VS Code dev environment.
- **Noir** (`nargo`) + **Barretenberg** (`bb`, UltraHonk). Versions validated in
  Phase 0/1 were `nargo 1.0.0-beta.20` and `bb 5.0.0-nightly.20260324`. **Confirmed in use
  on the Linux dev machine as of M3.2:** `nargo` (beta.20, binary at `/tmp/nargo`, not on
  `$PATH`) and `bb 5.0.0-nightly.20260324` (installed via the official `bbup` installer to
  `~/.bb`, added to `$PATH`). **Version pinning matters:** the circuit's `nargo`/`bb`
  versions must match what the proving bridge expects (e.g. `zkpassport/noir_rs` is tagged
  to `v1.0.0-beta.19-1`; beta-channel skew breaks). Pin the whole toolchain together.
- **Mobile proving is a supported path, not an open question.** `zkpassport/noir_rs` (Rust
  crate, UltraHonk via barretenberg-rs) generates/verifies Noir proofs on-device, with
  maintained mobile wrappers — **Swoir** (iOS) and **noir_android** (Android) — and
  documented Android cross-compilation. zkpassport ships a production mobile ZK app on it.
- **FFI:** the remaining work is the **Flutter/Dart glue**, since the wrappers are Swift /
  Kotlin / React Native, not Dart. Two routes: `flutter_rust_bridge` (auto-generated
  Dart↔Rust binding directly over noir_rs), or a Flutter **platform channel** to the
  Kotlin noir_android layer. This is bounded integration, not novel research. The one real
  perf question is whether the **48-generation tier (~943k gates)** proves acceptably on a
  ≥4 GB phone (the 12/24 tiers are effectively validated by the ~24 s / 409k Pixel 6
  smoketest). Treat the first Dart round trip + the 48-tier measurement as a spike.
- `bootstrap.sh` (to be written) sets up the full toolchain reproducibly.

## Working discipline

- **Test-against-vectors first.** When changing the circuit or the stepper, add/adjust
  the golden vector before or alongside the change; run the full corpus before commit.
- **Pair each constraint with the negative vector that fails without it** (see
  `CIRCUIT_IO.md` §10/§11). That pairing is what makes a later security review meaningful.
- **Small, focused commits with clear messages.** Soren is at an intermediate Git level —
  prefer legible history over clever rebasing; explain any non-obvious Git operation.
- **When uncertain about architecture or an open design flag, stop and ask** rather than
  guessing. Confabulated structure is expensive to unwind. Surfacing a blocker early is
  always correct.
- **Explain reasoning in PRs/summaries** so Soren can learn the modern tooling and
  exercise judgment — this is a learning project as well as a build.

## Scope — what to build now, and what NOT to

**In scope (the cryptographic-core tracer bullet):**
inscribe a grid → generate a proof (via FFI, on device) → persist it → verify it. The
circuit, the I/O serialization, the golden+negative vectors, the FFI bridge, and minimal
persistence. Build order is in the build plan; the security-reviewable milestone is
"circuit passes the full positive + negative corpus."

**Explicitly OUT of scope for now — do not build:**
- Battlefield, movement, targeting, summons, combat resolution.
- Networking / transport adapters (BLE, LAN, Nearby, Wi-Fi Direct).
- Spellbook/bestiary UI, inscription UI polish, dominance coloring.
- Sorcerer-mode sensors (verbal/somatic/movement).
- Master/Apprentice, scrolls, ELO, match records (beyond reserving struct fields).
- Talewright / story system.
- Anything behind a `[DECISION — needs Soren]` or `[TODO — playtest]` flag.

If a task seems to require one of these, it's a sign to stop and confirm scope, not to
expand it.

## Bug Avoidance Reminders
1. Thread-pool sizing requires HARDWARE_CONCURRENCY env set at ctor time — see M3_findings
2. bundled-VK path must not oversize SRS — see M3_findings
3. After touching anything under `ffi/src/`, run `bash scripts/check_ffi_fresh.sh`
   before `flutter run`/`flutter build apk` on Android. A stale jniLibs `.so` installs
   fine and crashes on launch with a cryptic "Content hash on Dart side is different
   from Rust side" error instead of failing the build — see M4_findings M4.6. The fix
   (`bash scripts/build_android_ffi.sh`) is one command; the check just remembers it
   needs to run.
4. A real verifier must call `initSrsCached` (or otherwise init the SRS/CRS) before its
   first `verify_ultra_honk`, even if it never proves in that session — the global CRS
   isn't initialized by anything else on a pure-verify path. See M4_findings M4.6.
