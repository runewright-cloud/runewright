# Runewright — Circuit I/O Contract (`CIRCUIT_IO.md`)

*The byte-level interface contract between the Noir circuit (`ca_lookup`), the Dart
stepper/client, and any future port. If the circuit and the client disagree on a
single bit of this, **nothing verifies**. This is the document Claude Code reads
before touching circuit or serialization code.*

**Status legend**
- `[FIXED]` — determined by mathematics (BN254 field size, Poseidon2 shape) or by a
  ratified design decision. Do not change without a design conversation.
- `[CONFIRMED]` — verified against `stepper.dart` / `ca_run.dart` / `hex_grid.dart`
  during M1 ratification pass. The stepper won where there was a discrepancy.
- `[BLOCKER]` — a confirmed discrepancy that requires Soren's decision before M3
  circuit work begins. Documented in `test/engine/ca_run_test.dart`.

## 0. The oracle principle (read first)

`stepper.dart` is the **canonical definition** of the CA's behaviour and of every
ordering/enum below — not this document, and not the prose design doc. This contract
exists to *pin down the interface*, but where it describes the CA's internal
encodings, it is a transcription of the implementation, not an authority over it.

Concretely: the golden vectors (`GOLDEN_VECTORS.md`) are generated **by running the
stepper**, and the circuit must reproduce them. That makes the stepper the oracle and
the vectors the contract enforcement mechanism. Any ambiguity here is resolved by
"what does the stepper actually do," confirmed by a golden vector.

## 2. Grid cell ordering `[CONFIRMED]`

The grid is a flat array of **469 cells** (radius-12 hex, `1 + 3·12·13 = 469`).

**Ordering: q×r scan** — confirmed from `HexGrid(12)` constructor in `hex_grid.dart`
and `all_cells()` in `gen_grid_constants.py`:

```
index = 0
for q in -12 .. +12:
    r_min = max(-12, -q - 12)
    r_max = min( 12, -q + 12)
    for r in r_min .. r_max:
        cells[index] = (q, r)
        index += 1
```

Key landmarks:
- **Index 0** = `(q=-12, r=0)` — a **border cell** (ring 12). *Not the center.*
- **Index 234** = `(q=0, r=0)` — the **center cell**.
- **Index 468** = `(q=12, r=0)` — a border cell.

> `seeds.example.json` (and early test seeds) had a bug: `active_cells: [0]` for the
> "single center" anchor. Index 0 is a border cell. The correct index is **234**.
> Fixed in `test_vectors/seeds.json`.

**Regions** are defined by hex distance `d = max(|q|, |r|, |q+r|)`, **not** by flat
index ranges. In q×r scan order, border and buffer cells are scattered throughout
the array — there is no contiguous block like "indices 397..468 = border":

| Region | Criterion | Cell count |
|---|---|---|
| Inscribable | d ≤ 8 | 217 |
| Buffer | 9 ≤ d ≤ 11 | 180 |
| Border | d = 12 | 72 |
| **Total** | | **469** |

For the circuit, use the `IS_BORDER[469]` boolean array generated by
`gen_grid_constants.py` (and, once added, `IS_INSCRIBABLE[469]` or an equivalent
distance-check constant) to identify which cells must be zero at T=0.

**`NEIGHBORS` slot order is semantic, not just a set `[confirmed satisfied 2026-06-23]`:**
the ink ruleset's Rule A and Rule B both need to know which neighbor is *opposite* which
(the old count-based rules were order-blind, so this was never load-bearing before).
`NEIGHBORS[i][6]` must be emitted in an order where slot `k` and slot `(k+3) % 6` are
antipodal, matching `ink_step.dart`'s `InkStep.directions`:
`(+1,0), (+1,-1), (0,-1), (-1,0), (-1,+1), (0,+1)` — giving axis pairs `(0,3), (1,4), (2,5)`
with no separate axis constant needed. Verified directly against the live
`circuits/ca_v2_4_tier12/src/constants.nr` and `scripts/gen_grid_constants.py`'s `DIRS`
constant: **the ordering already matches exactly** (decoded cell 0 = `(-12,0)` and cell 14
= `(-11,0)`'s `NEIGHBORS` rows by hand against this convention) — no regeneration needed.
Off-grid neighbor slots (`SENTINEL` = `N`) already read as inactive in the main loop,
matching `ink_step.dart`'s out-of-grid-is-inactive convention.

**`GRID_ORDERING_v2.md`** is the canonical generated companion; it confirms this
ordering and documents the region boundaries and border zone assignment.

> **STALE NOTE in GRID_ORDERING_v2.md:** its commitment section describes the Phase 1.5
> sponge `Poseidon2_sponge(grid_state[0..468] || T)`. That is superseded by the §4
> design here (`Poseidon2(packed[0], packed[1])`, grid-only). The ordering/boundary
> sections of GRID_ORDERING_v2.md are correct; the commitment section is not.

## 3. Grid packing (before hashing) `[FIXED]`

The commitment hashes a **packed** grid, not 469 separate field elements.

- BN254 scalar field modulus `r` is a 254-bit prime; pack **≤ 253 bits per field**
  to stay strictly below `r`.
- 469 bits → **2 field elements**:
  - `packed[0] = Σ_{i=0}^{252} cell[i] · 2^i`   (cells 0–252, 253 bits)
  - `packed[1] = Σ_{i=253}^{468} cell[i] · 2^(i−253)`   (cells 253–468, 216 bits)
- Bit `i` corresponds to cell index `i` in the §2 ordering. Document this split in
  `GRID_ORDERING.md` alongside the ordering.

This is nearly free in-circuit (two weighted sums over values already constrained to
{0,1}) and collapses the commitment to a single Poseidon2 permutation.

## 4. Commitment scheme `[FIXED, construction pinned 2026-06-16]`

```
commitment = Poseidon2(packed[0], packed[1])
```

- Poseidon2 over BN254, state size 4, rate 3, capacity 1 (matches Noir stdlib). Two
  inputs fit in one permutation.
- **Exact in-circuit construction (beta.20):** the stdlib's `Poseidon2::hash` is
  `pub(crate)` — not callable from a user circuit. The only public primitive is
  `std::hash::poseidon2_permutation`. Both this commitment and the §5 owner-binding hash
  must replicate the fixed-length-2 sponge by hand, exactly as `Poseidon2::hash([a, b],
  2)` does internally:
  ```
  let iv: Field = 2 * 18446744073709551616;       // 2 * 2^64, message_size=2 encoded in IV
  let mut state: [Field; 4] = [a, b, 0, iv];
  state = std::hash::poseidon2_permutation(state, 4);
  result = state[0];
  ```
  This is bit-for-bit identical to `Poseidon2::hash([a,b], 2)` (traced from
  `noir_stdlib/src/hash/poseidon2.nr`: `new(iv)` seeds `state[3]=iv`; absorbing two inputs
  with `cache_size < RATE` just buffers them into `cache[0..2]`; the fixed-length path
  skips the variable-length `absorb(1)`; `squeeze()`'s `perform_duplex` adds `cache[0..2]`
  into `state[0..2]` and permutes). Implement this as one shared helper
  (`fn poseidon2_hash2(a: Field, b: Field) -> Field`) and use it for both §4 and §5 so
  there is exactly one place this construction lives.
- **Grid-only.** `T`, `owner_pubkey`, and `ruleset_version` are **NOT** in the
  commitment — they are separate public inputs.
- **No salt.** Same grid → same commitment, by design, so counter charms target a
  rune at every step count, owner, and loan state. (Mystery spells and counter-charm
  *battle* commitments are a *different*, salted commitment — out of scope here.)
- **The client never recomputes this.** Dart reads `commitment` from the prover's
  public inputs and treats it as opaque. **Never reimplement Poseidon2 in Dart.**

## 5. `owner_pubkey` representation `[LOCKED in-circuit form 2026-06-16, CONFIRM byte order]`

**Canonical in-circuit binding, locked as of M3.1 — do not change:**

```
owner_pubkey == poseidon2_hash2(key_hi, key_lo)     // §4's fixed-length-2 construction
```

Fixed hash construction (the §4 `poseidon2_hash2` helper, equivalent to
`Poseidon2::hash([key_hi, key_lo], 2)` but expressed via the public
`poseidon2_permutation` primitive since the stdlib struct isn't externally callable),
fixed arity 2, fixed `[key_hi, key_lo]` ordering, **binds the pubkey halves only — nothing
else.** This constraint (with
`key_hi`/`key_lo` as private witness inputs, §9) is committed to the verification key
from the first v2.4 circuit onward specifically so the VK never has to change when the
identity module ships (see M3 Amendment 1 — VK stability is about gate shape, not public
input presence). **If a future identity design wants to bind a domain separator, a
nonce, or anything beyond the two pubkey halves, or wants a different arity/hash/order,
that is a new public input and a VK-breaking change — it must NOT be folded into this
hash.** Treat this binding as closed.

The inscriber's identity key is **Ed25519** (32-byte public key). A 256-bit key does
not fit in one BN254 field, so the circuit binds a **hash** of it:

```
owner_pubkey = Poseidon2( key_hi, key_lo )
```
- Split the 32-byte Ed25519 public key into two 16-byte halves (128 bits each, well
  under 253). `key_hi` = first 16 bytes, `key_lo` = last 16 bytes, under a **fixed,
  documented byte order** (propose little-endian as emitted by the Dart `ed25519`
  lib — `[CONFIRM vs stepper/client]`).
- The verifying client recomputes `Poseidon2(split(presented_key))` and checks equality.
- **All signatures are off-circuit Ed25519.** The circuit never verifies a signature.
  The cast-time challenge, loan certificates, scrolls, and match records are all
  Ed25519 signed/verified in Dart. The circuit's only job re: identity is to *bind*
  `owner_pubkey` as a public input so a replayed proof carries the original owner.

> Smoketest worth doing once (cheap insurance): confirm the toolchain genuinely binds
> an otherwise-unused public input into the verification key. A one-line dummy
> constraint referencing `owner_pubkey` (e.g. `assert(owner_pubkey == owner_pubkey)`
> or feeding it into a hash) guarantees it can't be stripped.

## 6. `ruleset_version` `[FIXED, locked 2026-06-16; bumped to 2 for the ink substrate]`

A small integer public input (an "arcana edition") — the rule-set **epoch**. Pinned to
`global RULESET_VERSION: Field = 2` (bumped from `1`) and asserted in-circuit
(`assert(ruleset_version == RULESET_VERSION)`), for the same VK-stability reason as §5.
The match handshake negotiates it; clients carry verifiers for the last N versions.
Binding it as a public input means a proof is only valid against the circuit version it
was generated for — so a future balance patch doesn't silently validate old proofs
against new rules.

**The bump, concretely:** the ink-substrate neutral ruleset (§10.5 — Rules A/B/E replacing
the old count-based neutral baseline, supreme-gated dispatch, tie-aware decay) is exactly
the "future consensus-visible CA rule change" this section anticipated — a deliberate,
VK-breaking version bump, not a redefinition of `1` in place. Nothing has shipped under
`RULESET_VERSION = 1`, so there are no proofs to orphan.

**Distinction from the §5 lock:** bumping `RULESET_VERSION` on a future consensus-visible
CA rule change is an *intentional* VK change — it deliberately makes incompatible
rule-sets non-interoperable and prevents replaying old proofs against new rules. That is
different from the §5 owner-binding lock, whose entire purpose is to make the *identity*
layer's eventual arrival **not** churn the VK. Don't mistake a deliberate version-bump
VK change for a regression of the §5 guarantee.

## 7. `T`, tiers, and padding semantics `[FIXED — confirm the masking model vs stepper]`

- **Three circuit tiers: `tier_max ∈ {12, 24, 48}`.** Noir arrays are compile-time
  sized, so T can't be a free runtime variable. Instead of one circuit (caps spectacle)
  or one-per-T (a VK zoo), there are **three** compiled circuits, sized 12 / 24 / 48.
  Each tier's trajectory/flag arrays are `[Field; tier_max]`.
- The **match handshake negotiates `ruleset_version` AND tier**, picking the **smallest
  tier whose `tier_max ≥ the spell's declared T`.** (A T=6 spell uses the 12-tier; a
  T=30 spell uses the 48-tier.)
- `T` (active generation count) is a **public input**, constrained `1 ≤ T ≤ tier_max`
  for whichever tier circuit is used.
- **Masking model `[CORRECTED 2026-06-16 — see M3.0 review]`:** within its tier, the
  circuit always simulates `tier_max` generations internally (a fixed-size circuit loop
  can't stop early — cell states keep evolving past `T`), but **every public output is
  masked by `gen < T`, not just `border_activations`.** This matches the canonical Dart
  oracle, `ca_run.dart:runStepper`, which stops accumulating at `T` and leaves the rest
  of `dominanceTrajectory` / `supremeFlags` at their zero-filled default. The earlier
  text in this section ("trajectory/flags past T are real but unconsumed") described a
  design that was never implemented Dart-side; per CLAUDE.md, Dart is canonical, so the
  circuit is corrected to match `ca_run.dart`, not the reverse.
  - `border_activations` = activation counts summed over generations `0 .. T−1`
    (per-generation accumulation **masked by `gen < T`**). ← security-sensitive; see §11.
  - `dominance_trajectory[g]` and `supreme_dominance_flags[g]` are **forced to 0** for
    `g ≥ T` (masked, matching `ca_run.dart`'s zero-fill — not real CA output). `T` is
    public and bound either way, so masking hides no information; it simply matches what
    the Dart oracle actually does, which is what the two-oracle harness compares against.
- **Three VKs per ruleset version**, not one and not a zoo. Proving is
  inscription-time, never battle-time, so the yellow tier's weight is acceptable and
  self-selected.

  **`[MEASURED 2026-06-23/24 — RULESET_VERSION 2, all tiers, Pixel 6]`:** (`bb gates`
  on compiled `ca_v2_4_tier{N}.json`; prove times median of 3 warm runs each)

  | Tier | ACIR opcodes | Padded bucket    | Headroom | Warm prove | Full inscription | Peak RSS  |
  |------|-------------|------------------|----------|------------|------------------|-----------|
  | 12   | 388,374     | 2^19 (524,288)   | ~136k    | ~12.7 s    | ~15.8 s          | —         |
  | 24   | 807,831     | 2^20 (1,048,576) | ~241k    | ~24.5 s    | ~31.5 s          | ~2.1 GB   |
  | 48   | 1,646,745   | 2^21 (2,097,152) | ~450k    | ~48.9 s    | ~62 s            | ~4.3 GB   |

  "Full inscription" = warm prove + SRS disk-read (tier-24 ~7 s, tier-48 ~13 s).
  Tier-12 RSS not captured in the M3.4 spike; estimated ~1 GB by halving tier-24.
  Scaling is approximately linear in tier_max (388k × 2 = 776k estimate vs 808k actual

- Claiming a smaller `T` yields a weaker spell **and** lower mana cost
  (`mana = ceil(cells · 1.25^max(0, T−4))`), so there's no incentive to lie about it.
  Note the two regimes: high-cell spells are mana-gated; low-seed bloomers are
  *tier*-gated (barely taxed by mana), which is the intended clever-engineering reward.

  against a newer `1.05` + transition-tax mana model referenced elsewhere (plus deferred

## 10. Constraints the circuit MUST enforce (positive) `[FIXED]`

1. Every `grid_state[i] ∈ {0, 1}` (boolean) — enforced for **all 469** cells.
2. Buffer + border cells (`i ≥ 217`) are `0` at T=0.
3. `packed[0]`, `packed[1]` equal the §3 weighted sums of `grid_state`.
4. `commitment == Poseidon2(packed[0], packed[1])`.
5. Running the CA for `tier_max` generations from `grid_state` produces exactly the
   declared `dominance_trajectory` and `supreme_dominance_flags`, under the rules below.
   The four elemental count-rule sets (`ca_rules.dart`) are **unchanged**. The neutral
   branch, the dispatch gate, and decay/tie handling are **`RULESET_VERSION 2` changes**
   — canonical oracle: `lib/engine/ink_step.dart` (neutral branch) and `ca_run.dart`'s
   `advanceDominance` (dispatch/decay/ties), both reached via `stepper.dart`'s
   `CAStep.step`. Where this section and the Dart disagree, the Dart wins.

   **Neutral branch — the ink ruleset `[CHANGED, RULESET_VERSION 2]`:** birth-only,
   synchronous, computed from the prior generation, union-applied — no inscribable/buffer
   cell ever deactivates (see §10.10). Replaces the old hex-Conway-2/2 neutral baseline.
   - *Rule A (gap-fill/merge), distance-1:* an inactive cell with ≥1 complete antipodal
     axis (both opposite neighbors active, per the §2 slot convention) becomes active.
   - *Rule B (tip extension), distance-2 — the cost driver:* an active cell with exactly
     one active neighbor activates that neighbor's antipode. Encoded as two distance-1
     passes with an intermediate witness — see the dedicated subsection below and §10.11.
   - *Rule E (serif flare), distance-1, parity-gated:* on a pulse generation (see the
     generation-indexing subsection below), an inactive cell with exactly one active
     neighbor becomes active — birth-on-1 gated by parity, folded into the lookup as a
     parity-selected row.
   - *Rule C (collision burst): removed.* Was a 7-cell scatter (self + 6 neighbors) on
     ≥2 complete axes; replaced by Rule E's cheaper distance-1 parity pulse.
   - *Rule D (no deaths):* realized structurally as the union below, not as a rule of its
     own; enforced by §10.10. Border cells are the unconditional exception (next
     paragraph after the dispatch/decay subsections).

   **Rule dispatch — gated behind supreme dominance `[CHANGED, RULESET_VERSION 2]`:**
   previously the dominant element's rule set applied whenever that element merely led on
   pressure. Now:
   ```
   rule(g) = (supreme_dominance_flags[g] == 1)
               ? elemental_rules[ dominant_element(g) ]
               : neutral_ink_rules
   ```
   `supreme_dominance_flags[g]` is computed **exactly as before** (dominant zone's net
   counter strictly exceeds the other three combined) and is now a **dispatch signal as
   well as a public output** — the value gating evolution and the value emitted must be
   the literal same computation, not a parallel recompute, or the declared flags and the
   actual evolution can diverge. `dominance_trajectory[g]` still reports the **dominant**
   element (the spell's elemental signature) even on generations where the grid evolves
   under neutral ink because that element wasn't supreme — dispatch and trajectory are
   intentionally decoupled; trajectory does NOT follow dispatch. Pressure accumulates
   every generation regardless of dispatch, including neutral ones (+1 per border
   activation in its zone) — there is no "reset on neutral" anywhere; only decay
   (next subsection) ever lowers a zone's counter.

   **Decay, ties, and dominance reporting `[CHANGED, RULESET_VERSION 2]`:** the old
   "only the dominant element decays, by `floor((gen+1)/2)`" generalizes. Per generation
   `g`, with `D = floor((gen+1)/2)`, let `maxP` be the highest net pressure across the
   four elements and `k` the count of elements holding `maxP`:
   - If `maxP > 0`: every element at `maxP` decays by `ceil(D / k)` (`= (D + k − 1) / k`),
     floored at 0. A unique leader (`k = 1`) decays by the full `D` — identical to the old
     behavior in the no-tie case. A `k`-way tie splits the rounded-up decay across the
     tied set.
   - If `maxP == 0`: nothing decays.
   - **Tie reporting:** a tie (`k ≥ 2` at `maxP`) reports **no dominant** —
     `dominance_trajectory[g] = 0` — and can never be supreme (a tied zone's pressure is
     at most half the total, so `pDom*2 > total` is unreachable for any tied zone). A
     unique `maxP` element is the dominant, reported as today. This replaces the old
     sticky-tie rule ("a tie keeps the previous leader") *for reporting only*; dispatch
     was never affected by the distinction since a tie can't be supreme either way.
   (Confirmed by stepper: `CAStep.step` increments `stepCount` before returning, so
   at generation `gen` the returned grid has `stepCount = gen+1` and `D = stepCount
   ~/ 2`. Sequence gen 0..6: **0, 1, 1, 2, 2, 3, 3**. NOT `floor(gen/2)`. This `D` figure
   is unchanged by the above — only how it's split across the max-pressure set changed.)

   **Generation indexing / the pulse off-by-one `[TRAP — pin with a golden vector]`:**
   `ink_step.dart` is 1-indexed (`generation == stepCount`) and pulses when
   `generation % cadence == 0` (generations 4, 8, 12, …). The circuit's loop is 0-indexed
   `g`, with the same `stepCount = g + 1` convention the decay formula above already uses.
   The circuit's pulse predicate is therefore `pulse(g) = ((g + 1) % cadence == 0)`,
   firing at `g ∈ {3, 7, 11, ...}` — NOT `g % cadence == 0`. `cadence = 4`, pinned as a
   circuit global matching `InkRules`' production default (the sandbox may vary it; the
   circuit is frozen at production). A golden vector with `T` spanning a pulse boundary
   (`T ≥ 4`, seed with a free tip) must confirm the flare lands on the same generation in
   both oracles — this is the single easiest place to introduce a silent off-by-one.

   **Border-cell evolution `[CORRECTED 2026-06-16]`:** per `stepper.dart:15-35`, every
   border cell — alive or dead — transitions to **dead** next generation unconditionally.
   A dead border cell satisfying a birth condition still counts as an activation toward
   `border_activations`, but never itself becomes alive (it must not occupy the cell or
   count toward a ring-11 neighbor's count, or it would suppress future activations on
   that same cell). Unchanged by the ink substrate except for *which* birth conditions
   trigger the activation — the trigger set is now the ink birth conditions (`bornA OR
   bornB OR (pulse AND bornSerif)`) rather than the old count rule. The Phase 1.5 proxy
   circuit (`ca_lookup_v2`) got the force-to-0 part wrong; v2.4 forces `next_grid[i] = 0`
   for every `IS_BORDER[i]`, independent of the activation check.

   **Rule B as two distance-1 passes:** Rule B is scatter (an active cell writes onto a
   neighbor's antipode); gather form needs each cell to inspect its neighbors' neighbors
   — distance-2. Decompose into two distance-1 passes per generation with one
   intermediate witness array `b_ext: [Field; N]`:
   - *Pass 1 — per cell `X`, compute `b_ext[X] ∈ {0..6}`* (0 = not a B-source; 1..6 =
     extension direction + 1): `X` is a B-source iff `prev[X] == 1` AND
     active-neighbor-count(`X`) == 1. When it is, the single active neighbor's slot is
     `s` (well-defined precisely because the count is 1), the extension direction is the
     antipode `d_ext = (s + 3) % 6`, and `b_ext[X] = d_ext + 1`. Otherwise `b_ext[X] = 0`.
   - *Pass 2 — per non-border cell `Y`, gather:* `bornB[Y]` = OR over slots `e ∈ {0..5}`
     of: let `X = NEIGHBORS[Y][e]`; `X` in-grid AND `b_ext[X] == ((e + 3) % 6) + 1`. (If
     `X` is at slot `e` from `Y`, `Y` is at slot `(e+3)%6` from `X`, so `X` extends into
     `Y` exactly when `X`'s extension direction equals `(e+3)%6`.)
   `b_ext` is recomputed every generation (B is not parity-gated) and is attack surface
   — see §10.11 / §11.9: a prover must not be able to supply an arbitrary `b_ext`.

   New neutral-branch next-state for a **non-border** cell `Y`:
   ```
   next[Y] = OR(
       prev[Y],                      // Rule D — monotone union, never deactivates
       bornA[Y],                     // Rule A
       bornB[Y],                     // Rule B (from the b_ext intermediate above)
       pulse ? bornSerif[Y] : 0      // Rule E
   )
   ```
   where `bornA[Y] = (prev[Y] == 0) AND (Y has ≥1 complete axis)` and
   `bornSerif[Y] = (prev[Y] == 0) AND (active-neighbor-count(Y) == 1)`.
6. `border_activations` equals the per-element activation totals summed over
   generations `0 .. T−1` (masked by `gen < T`).
7. `dominance_trajectory[g] == 0` and `supreme_dominance_flags[g] == 0` for every
   `g ≥ T` (masked by `gen < T` — same backstop as #6; see §11 `neg_mask_abuse`).
8. `1 ≤ T ≤ tier_max` (for the tier circuit in use).
9. `owner_pubkey` and `ruleset_version` are bound (referenced so they're in the VK).
10. **Neutral monotonicity (Rule D) `[NEW, RULESET_VERSION 2]`:** in a neutral
    generation, every inscribable/buffer cell satisfies `next[i] ≥ prev[i]` (an active
    cell stays active). Automatic if `next` is built as the §10.5 union, but must be
    *enforced*, not merely emergent — otherwise a witness could claim a death to forge a
    different trajectory. Border cells are exempt (forced to 0 by the unchanged border
    rule, which overrides this).
11. **`b_ext` intermediate is correctly derived `[NEW, RULESET_VERSION 2]`:** each
    `b_ext[i]` equals the §10.5 Pass-1 function of `prev` and the neighborhood — a
    prover cannot supply an arbitrary intermediate. Constrain `b_ext[i]` against
    `prev[i]`, the neighbor bits, and the active-neighbor count.

## 11. What the circuit MUST REJECT (negative vectors) `[FIXED — Fable's hunting ground]`

ZK exploits are almost never "wrong answer"; they're an **under-constrained circuit
that accepts a witness it shouldn't.** This is the spell-leak / proof-forge surface.
Every item below must have a **negative golden vector** that the circuit *rejects*.
Items #1–#7 predate the ink substrate and all still apply unchanged as a *category*;
#4 (forged trajectory) and #5 (forged activations) now exercise the ink neutral
evolution as their oracle, so their *vector values* are regenerated against the new
`RULESET_VERSION 2` circuit, not their meaning.

1. **Non-boolean cell:** a `grid_state[i]` set to 2 (or any value ∉ {0,1}). If
   constraint §10.1 is missing on even one cell, packing/commitment math can be gamed.
2. **Illegally pre-seeded buffer/border:** any active cell at `i ≥ 217` at T=0.
3. **Commitment mismatch:** a witness grid that does not hash to the stated `commitment`.
4. **Forged trajectory:** declared `dominance_trajectory` / `supreme_dominance_flags`
   that don't match the true CA evolution of the witness grid.
5. **Forged activations:** declared `border_activations` not equal to the true masked
   sum over `0..T−1`.
6. **Mask abuse:** activations from generations `g ≥ T` leaking into `border_activations`,
   OR a non-zero `dominance_trajectory[g]` / `supreme_dominance_flags[g]` declared for
   `g ≥ T` (tests constraints §10.6/§10.7 — the masking is the subtle one).
7. **Out-of-range `T`:** `T = 0` or `T > tier_max` (T must fit the tier circuit proving it).
8. **Forged death (monotonicity break) `[NEW, RULESET_VERSION 2]`:** a neutral witness in
   which a live inscribable cell goes to 0 from one generation to the next. If §10.10 is
   missing, a prover can suppress births/cells to forge a cheaper-looking or different
   trajectory.
   > **SUBSUMED (2026-06-23):** discharged by `neutral_monotonicity_chain` positive vector — a 3-gen Rule B chain whose border-contact timing is causally dependent on every tip cell persisting; any monotonicity break shifts the contact generation and the wrong tier/gen fails the vector's exact expected values.
9. **Tampered `b_ext` `[NEW, RULESET_VERSION 2]`:** a witness supplying a `b_ext` entry
   that does not match its Pass-1 derivation (e.g. claiming a non-source cell extends, or
   a wrong direction) to manufacture an extra `bornB` activation. If §10.11 is missing,
   the two-pass intermediate is a free-form forgery vector — the most ink-specific new
   exploit surface; pair it with §10.11 explicitly.
   > **SUBSUMED (2026-06-23):** discharged by `neutral_evolution_composite` and `pulse_boundary` positive vectors — both exercise the full b_ext derivation path (Rule A gap-fill → multi-gen Rule B tip extension → serif), so a corrupt b_ext would shift border-contact generation and mismatch the vectors' commitment and trajectory; a dedicated forge-b_ext negative vector is the remaining gap and is deferred to M4 circuit constraint work.

> When CC implements §10, each constraint should be paired with the negative vector
> that fails if the constraint is dropped. That pairing is what makes "Fable reviewed
> it" mean something: the review checks the *reasoning*, the negative vectors check the
> *artifact*, and they catch different mistakes.

## 12. Identity & key custody (UI consequence, recorded here so it isn't lost)

- Keypair (Ed25519) is **generated on first launch**, stored on-device. No accounts,
  no server.
- **Losing the private key** → can't answer the cast-time challenge → can't *cast*
  spells you own (though the grids/proofs remain). Tell the player the key is theirs to
  keep safe.
- **Losing the spellbook** → lose the proofs and grid states themselves. Encourage
  backups.
- Counter-charm targeting *against* the player is unaffected by either loss (hash-based,
  owner-independent).
