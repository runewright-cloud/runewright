# Replay Harness — a golden corpus for the battle engine

*Status: built 2026-08-13, one script in the corpus. This is the safety net that
makes the `TurnLoop` split safe to attempt; it is not itself that refactor.*

---

## Why this exists

The August 2026 architecture review's headline recommendation is to split `turn_loop.dart`
(~7.7k lines) into protocol orchestration and deterministic resolution:

```
untrusted declaration → certified action → deterministic resolution
```

That is the right direction. It is also the most dangerous refactor available in this
codebase, and the review does not say how to do it safely. The failure mode is not a
crash or a failed test — it is a **subtle reordering that silently changes resolution**,
whose only tripwire in production is a state-hash mismatch on someone's phone, mid-duel,
three turns into a match that then forfeits.

`CLAUDE.md` already names the answer for the circuit:

> The corpus is *generated by running the stepper*; the circuit must reproduce it.

This is that discipline pointed at the battle engine. **The corpus is generated by running
the current engine; the refactored engine must reproduce it.**

The rule this establishes, for the duration of the refactor:

> **The intended change is "same behaviour, different structure." Any golden diff is
> therefore a bug until proven otherwise.**

## What a transcript records

Each scripted match produces one JSON golden under `test/battle/replay/golden/`. Per turn:

| Field | Role |
|---|---|
| `stateHash` | **Authoritative.** SHA-256 of `BattleState.toCanonicalBytes()`. |
| `events` | **Authoritative.** Per-type counts of the events the turn emitted. |
| `summary` | Diagnostic only. HP, mana, chain, position, entity counts. |
| `note` | The script's own narration of what the turn is for. |

### Why hashes rather than serialized state

Serializing the whole `BattleState` would be a large, brittle artifact that every new
field silently invalidates. It is also unnecessary: `toCanonicalBytes()` is *already* the
project's definition of the observable state of a match — it is what the two devices hash
at each other to agree they are still in the same game. Anything it excludes is, by
construction, not consensus state.

### Why events are recorded too

Events are **not** in `toCanonicalBytes()` — they drive UI playback, not consensus — so
the state hash cannot see them at all. They are still behaviour a refactor must preserve,
and they answer the one question a bare state hash cannot: *did the cast resolve, or
fizzle?* A spell that quietly stops resolving leaves `resolvedSpells` at 0 while the
canonical state still looks entirely plausible.

This earned its place immediately. The first script's casts produced no HP, terrain or
status change, which looked like a script that wasn't exercising anything. The event
counts showed `resolvedSpells: 2` — the casts *were* resolving; an Earth Barrier
(`earth/earth` → `EffectKind.barrier`) simply has nothing to reinforce on a battlefield
with no terrain. Without events that would have been an hour of debugging a non-problem.

### Why the summary is not authoritative

A bare hash tells you "turn 3 differs" and nothing else. The summary tells you *which
field moved*, which is usually the whole diagnosis. But it is deliberately shallow and
never compared as authority — a summary mismatch that leaves the hashes intact means the
extractor changed, not the engine.

## What it covers that unit tests cannot

Scripts run several turns against the same pair of loops, so they exercise the state that
lives *between* turns and is deliberately excluded from the canonical hash:

- `_drawSchedules`, `_drawSeedNonce` — hand refills and per-player RNG seeds
- `_seenPeerCommitments` — the duplicate-grid guard, which drives a **forfeit**
- `_ripplingNonce` — incremented across turns, unlike `_wildMagicNonce`/`_turbulentNonce`
  which reset each turn
- `_componentStartSeat` — casting order
- `PendingDelayedSpell`'s non-canonical fields — `origin`, `declaredRange`, and now
  `certified` (M4.15)

**That list is the review's §7 "latent divergence" concern, arrived at independently.**
Two clients can hold identical canonical hashes while differing in secondary state that
steers a later turn. A multi-turn transcript is the cheapest thing that can catch it, and
enumerating that set is most of the audit §7 asks for.

The harness also asserts **lockstep independently of the golden**: both devices' canonical
hashes must match each other every turn. That check stays live even while regenerating,
because two devices disagreeing with *each other* is a worse failure than disagreeing with
a recorded expectation.

## Using it

```bash
# Verify (runs as part of the normal suite)
flutter test test/battle/replay/

# Regenerate after an INTENTIONAL behaviour change
RUNEWRIGHT_REGEN_REPLAY=1 flutter test test/battle/replay/
```

Regeneration deliberately **fails the run**. A green regeneration would let expectations
be rewritten inside an ordinary test invocation unnoticed, and the entire value of a
golden corpus is that changing it is a conscious act. Re-run without the flag to verify.

A diff means one of three things, in descending order of likelihood:

1. **You changed behaviour on purpose.** Read the diff, confirm it says what you meant,
   regenerate, and justify it in the commit message.
2. **You changed behaviour by accident.** This is what the harness is for.
3. **You changed the script or the summary extractor.** Then the diff is noise — prefer
   not to, since it costs the corpus its history.

### Validating the harness itself

A golden corpus that cannot fail proves nothing, so it was checked the same way the §10/§11
negative vectors are: perturb the engine, confirm the corpus notices.

Worth recording, because it is a trap: the *first* perturbation attempted (chain
regression `-4` → `-2`) produced **no diff**, because both values clamp to zero for this
script's chain length. That is a badly chosen probe, not an insensitive harness. Changing
the chain credit (`2` → `3`) failed correctly and named turn 2. **When validating a
corpus, pick a perturbation you have confirmed is observable in the scripts you have.**

## Corpus roadmap

One script today: `delayed_cast_and_chain` — a Mystery declared turn 1 and fired turn 2,
with ordinary casts either side. Chosen first because it puts the most cross-turn
machinery in one place.

A script earns its place by exercising something that **spans turns**. Per-feature
coverage is what the engine unit tests are for. Worth adding before the refactor starts:

- **Spells that move the board.** The current script's Earth Barriers resolve but change
  no terrain, so board mutation is currently uncovered. This wants a fixture whose
  formula produces damage or terrain.
- **Draw/refill across several turns**, to pin `_drawSchedules` and `_drawSeedNonce`.
- **A summon that survives and acts** on later turns.
- **A counter charm** intercepting a delayed fire.
- **A forfeit path** — duplicate grid, or an unbacked enhancement claim.

## Relationship to the refactor

The harness is the precondition, not the work. The sequence:

1. **Corpus first**, broad enough that a behaviour change anywhere in resolution shows up.
   (We are at step 1.)
2. Extract deterministic resolution so it is independently callable, corpus green at every
   commit.
3. Only then consider the fuller `BattleProtocolDriver` / `BattleResolver` split.

Step 2 is where most of the value is: the review notes that simply *making deterministic
game resolution independently callable* is most of the benefit, without breaking every
effect into its own class.

**Do not begin step 2 while the corpus is one script.** The corpus is the only thing
standing between that refactor and a silent lockstep bug.
